## 1. Общая оценка архитектуры

Проект сделан заметно лучше среднего. Видна продуманность, а не «как получилось»:

| Что сделано хорошо | Где |

| Выполнение кода студентов вынесено в Piston (внешняя песочница), а не `eval`/`child_process` | `src/lib/code-runner/executor.ts` |

### Слабые места архитектуры (решения, а не баги)

**1.1. Нет слоя авторизации между actions и данными.** Права проверяются вручную в каждой функции: ~170 server actions, в каждой свой `if (role === ...)`. Работает ровно до первой забытой проверки — такие уже есть (см. 2.3).

**1.2. Модель ролей бинарная там, где ролей четыре.** По коду 31 раз встречается паттерн `role === "STUDENT" ? ограничить : показать всё`. Роль `PARENT` в дихотомию не попадает и трактуется как персонал. Следствия — 2.4.

**1.3. Валидаторы есть, но не работают.** В `src/validators/` 14 zod-схем, но в actions они импортируются через `import type` — **только как типы**. Реальный `safeParse` вызывается лишь в 5 файлах из 24 (`payment`, `lead`, `marketing`, `auth`, `email-verification`).

Проверить: `grep -n 'from "@/validators' src/actions/*.ts` — почти везде `import type`.

Пример: `createUserSchema` требует пароль ≥ 8 символов, но `createUser` (`src/actions/user-actions.ts:359`) её не вызывает — проверка живёт только в браузере. Server action — обычный сетевой эндпоинт, TypeScript его не защищает.

**1.4. Нет тестов.** 656 строк самописных скриптов (`scripts/check-billing.ts`, `check-billing-db.ts`, `check-attendance-db.ts`) покрывают биллинг и посещаемость. Ни одного теста на права доступа — при том что права здесь главная сложность. Тестового раннера нет, в CI тесты не гоняются.

**1.5. CI деплоит в прод напрямую с `main` без единой проверки.** `.github/workflows/deploy.yml`: нет `tsc`, нет `lint`, нет тестов, нет `concurrency`-группы (два пуша подряд = два параллельных деплоя с `migrate deploy`), нет бэкапа БД перед миграцией. Smoke-тест после деплоя есть (строки 94-105) — это плюс.

## 2. Уязвимости

### КРИТИЧНО

#### 2.1. Деактивация пользователя и смена роли не действуют до 30 дней

**Где:** `src/lib/auth.ts:161-182`

Сессия JWT, роль пишется в токен один раз при входе. Ни `jwt`, ни `session` callback не обращаются к БД. `isActive` проверяется **только** в момент логина (`src/lib/auth.ts:61`).

```ts
// src/lib/auth.ts:162
async jwt({ token, user }) {
  if (user) {          // <- только при первом входе
    token.role = user.role;
    token.id = user.id;
  }
  return token;        // дальше токен никогда не сверяется с БД
}
```

**Последствия:**
- `deactivateUser` (`src/actions/user-actions.ts:554`) ставит `isActive: false`, но уволенный сотрудник продолжает работать до истечения токена — дефолт Auth.js **30 дней**.
- Понижение ADMIN → TEACHER (`updateUser`, `src/actions/user-actions.ts:441`) не действует столько же.
- `resetPassword` (`src/actions/email-verification-actions.ts:139`) не выкидывает чужие сессии: угнавший аккаунт остаётся внутри после смены пароля.

**Починка:** в `jwt` callback перечитывать `isActive`/`role` из БД (можно с TTL 30–60 с, чтобы не бить в БД на каждый запрос), возвращать `null` при `isActive === false`. Добавить явный `session: { strategy: "jwt", maxAge: ... }`. Для инвалидации после сброса пароля — поле `sessionsValidFrom` в `User` и сверка с `token.iat`.

#### 2.2. Stored XSS через файл домашней работы → захват сессии преподавателя

**Цепочка:**

1. `src/app/api/homework/[homeworkId]/upload/route.ts:16` — расширение `.html` в `ALLOWED_EXTENSIONS` (там же `.svg` нет, но есть в `src/app/uploads/[...path]/route.ts:20`).
2. `src/app/api/homework/[homeworkId]/upload/route.ts:125` — `mimeType: file.type || "application/octet-stream"`. `file.type` берётся из `Content-Type` части multipart-запроса, то есть **полностью подконтролен студенту**.
3. `src/app/api/files/[fileId]/route.ts:54` — файл отдаётся с `"Content-Type": file.mimeType` **inline**, без `Content-Disposition`.
4. `src/components/homework/submission-review-page.tsx:452` — преподаватель открывает файл ссылкой `target="_blank"` **на том же origin**.

**Эксплуатация:** студент заливает `solution.html` с `Content-Type: text/html` → преподаватель открывает работу → скрипт студента выполняется в origin CRM с правами преподавателя/админа (доступ ко всем server actions от его имени).

`X-Content-Type-Options: nosniff` из `src/proxy.ts:150` здесь **не спасает**: тип объявлен явно, а не угадывается.

**Починка:**
- Игнорировать `file.type`; выводить MIME из расширения по белому списку на сервере.
- Для всего, кроме картинок, — `Content-Type: application/octet-stream` + `Content-Disposition: attachment`.
- Убрать `.html` (и `.svg` в `src/app/uploads/[...path]/route.ts:20`) из разрешённых, либо отдавать пользовательские файлы с отдельного домена.
- `src/app/api/files/[fileId]/download/route.ts:54` — `filename` в заголовке не экранируется; кавычка в имени файла ломает заголовок. Использовать `filename*=UTF-8''<encodeURIComponent>`, как уже сделано в экспорт-роутах.

#### 2.3. Полная выгрузка справочника учеников с телефонами и почтой — любому авторизованному

Функции обёрнуты в `withAuth`, но **без опции `roles`** — то есть доступны ученику и родителю:

| `getEnrolledStudents` | `src/actions/course-actions.ts:396` | всех учеников любого курса с email и телефоном |
| `getUngroupedStudents` | `src/actions/group-actions.ts:417` | то же по курсу |
| `getGroupDetails` | `src/actions/group-actions.ts:27` | состав любой группы с контактами |
| `getAttendanceSessions` | `src/actions/attendance-actions.ts:50` | всю посещаемость любого курса + email |
| `getAttendanceReport` | `src/actions/attendance-actions.ts:274` | матрицу посещаемости с email |

**Починка:** добавить `{ roles: ["ADMIN", "TEACHER"] }`; для роли TEACHER дополнительно ограничить своими курсами (образец правильной проверки — `src/actions/homework-review-actions.ts` `reviewSubmission`, где `course.teacherId !== session.user.id` → `forbidden`).

#### 2.4. Роль PARENT обходит все ограничения, написанные для учеников

Санитизация правильных ответов написана как `if (role === "STUDENT")`:

```ts
// src/actions/assessment-actions.ts:46 и :85
if (session.user.role === "STUDENT") {
  // вырезать o.isCorrect
}
return { success: true, data: assessment };  // PARENT приходит сюда
```

Родитель — не STUDENT, поэтому `getAssessment` и `getTestByLesson` возвращают ему **`isCorrect` по всем вариантам ответов**, то есть готовые ключи ко всем тестам и экзаменам школы.

Тот же паттерн в остальных местах даёт роли PARENT:
- неопубликованные уроки — `src/actions/lesson-actions.ts:16`, `:92`, `:108`
- неопубликованные тесты/экзамены — `src/actions/assessment-actions.ts:114`
- неопубликованные ДЗ — `src/actions/homework-actions.ts:304`

Отдельно: `src/actions/attendance-actions.ts:335` `getStudentAttendance(studentId?)` — для роли, отличной от STUDENT, `studentId` берётся из аргумента **без проверки родства**; родитель читает посещаемость любого ребёнка школы, не только своего.

Роль PARENT реальна и создаётся: `src/validators/user.ts:3`, `src/actions/parent-actions.ts` `createParentForStudent`, кабинет `src/app/[locale]/(dashboard)/my-children/page.tsx`.

**Починка:** заменить `role === "STUDENT"` на явный белый список привилегированных ролей — `["ADMIN","TEACHER"].includes(role)`. Все 31 место: `grep -rn 'role === "STUDENT"' src/`. Для PARENT в `getStudentAttendance` — сверять запрошенного ученика со связями `ParentStudent` (образец правильной проверки: `src/actions/parent-actions.ts:71` в `getParentChildren`).

#### 2.5. Неаутентифицированный эндпоинт `getAccessibleStudentIds`

**Где:** `src/actions/parent-actions.ts:33`

```ts
"use server";
...
```

## 3. Ошибки бизнес-логики

### 3.1. Накрутка баллов за тест дублированием ответа

**Где:** `src/actions/assessment-actions.ts:525-566`

`data.answers` не дедуплицируется, а `maxScore` накапливается **по каждой записи в массиве**:

```ts
const answersWithScoring = data.answers.map((answer) => {
  const question = assessment.questions.find((q) => q.id === answer.questionId);
  ...
  maxScore += question.points;      // :539 — по записи, а не по вопросу
  ...
});
// :561 — неотвеченные вопросы добавляются в maxScore только один раз
```

Арифметика:
```
2 вопроса по 1 баллу, студент знает только первый.
Честно:                    maxScore=2,  score=1  → 50%
Отправить Q1 десять раз:   maxScore=11, score=10 → 91%
```

Чем больше дубликатов, тем ближе к 100%. Отправляется прямым вызовом server action.

**Починка:** схлопывать `answers` по `questionId` (первое вхождение), `maxScore` считать строго как `sum(assessment.questions.points)`.

### 3.2. Проверка допуска к экзамену чисто декоративная

**Где:** `src/actions/assessment-actions.ts:426` `checkAssessmentEligibility`

Проверяет, сданы ли все тесты уроков курса. Вызывается только из UI. `submitAssessmentAttempt` (`:489`) её **не вызывает** — прямой вызов action сдаёт экзамен без единого сданного теста.

### 3.3. Ограничение по времени на тест не существует на сервере

`Assessment.timeLimitMin` нигде не проверяется. `AssessmentAttempt` создаётся только в момент отправки (`src/actions/assessment-actions.ts:574`), то есть `startedAt ≈ completedAt` всегда. Таймер полностью клиентский.

**Починка:** создавать `AssessmentAttempt` при старте (со `startedAt`), при отправке сверять `Date.now() - startedAt` с `timeLimitMin`.

### 3.4. Лимит попыток не защищён от гонки

Три места с комментарием «race condition protection», где защиты нет:
- `src/actions/assessment-actions.ts:572`
- `src/lib/homework-submission.ts:37`
- `src/app/api/homework/[homeworkId]/upload/route.ts:102`

`count()` внутри транзакции при уровне изоляции READ COMMITTED (дефолт Prisma/Postgres) от гонки не защищает: два параллельных запроса оба увидят N и оба вставят.

**Починка:** уникальный индекс `@@unique([homeworkId, studentId, attemptNumber])` на `Submission` и `@@unique([assessmentId, studentId, attemptNumber])` на `AssessmentAttempt` (потребует добавить поле `attemptNumber` в `AssessmentAttempt`), либо `SELECT ... FOR UPDATE` на строку `Enrollment`.

### 3.5. Скрытые тест-кейсы утекают студенту после первой попытки

**Где:** `src/actions/homework-actions.ts:368`

```ts
const submissions = await prisma.submission.findMany({
  where: { homeworkId, studentId: session.user.id },
  include: {
    testResults: {
      include: {
        testCase: {
          select: { id: true, input: true, expected: true, isHidden: true, ... },
          //                 ^^^^^^^^^^^^^^^^^^^^^^ включая isHidden: true
        },
      },
    },
  },
});
```

Строкой выше (`:345`) скрытые тест-кейсы корректно отфильтрованы (`where: { isHidden: false }`) — намерение было правильное, второй запрос его обходит. UI их не рисует (`src/components/homework/homework-view.tsx:381` жёстко ставит `isHidden: false` для отображаемых), но данные лежат в ответе сервера и читаются из сетевой панели.

**Починка:** не выбирать `input`/`expected` для `testCase` с `isHidden: true`, либо вырезать их после выборки.

### 3.6. `manualScore` не ограничен сверху

`src/actions/homework-review-actions.ts` `reviewSubmission` — преподаватель может поставить балл больше `homework.maxScore`. Валидации нет.

### 3.7. Нет защиты последнего администратора

# 7. Оценка выбора технологий

## 7.1. Два компонента не работают в проде

**Piston не задеплоен.** Сервис `piston` есть в `docker-compose.yml` (dev, строки 19-32), но в `docker-compose.prod.yml` его **нет**, и `PISTON_API_URL` **не передан** в `environment:` контейнера `app` (строки 52-73). Docker Compose не пробрасывает переменные из `.env` в контейнер автоматически — только те, что перечислены в `environment:`. Значит в проде берётся дефолт из `src/lib/code-runner/config.ts:22` — `http://localhost:2000/api/v2`, а внутри контейнера `app` это он сам. **Автопроверка кода в продакшене не работает**: каждая сдача CODE-задания падает в `status: ERROR`.

*Починка:* добавить сервис `piston` в `docker-compose.prod.yml` (память: он не влезет в оставшийся бюджет 956 МБ — см. 7.5) либо явно указать `PISTON_API_URL` на внешний инстанс. До этого — либо чинить, либо честно отключить CODE-задания в UI.

**Upstash Redis не настроен → rate limiting в проде отключён.** `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` отсутствуют в `docker-compose.prod.yml`. Следствие в `src/lib/rate-limit.ts:9` — `createRedis()` возвращает `null`, значит `authLimiter`, `apiLimiter`, `uploadLimiter`, `leadLimiter` все `null`. `applyRateLimit` (`:53`) при `null` возвращает `null` = «пропустить», `isWithinRateLimit` (`:83`) возвращает `true`.

Не работают в проде:
- `uploadLimiter` на `/api/v1/upload/video` (лимит 500 МБ на файл, см. 4.1) и `/api/v1/upload/image`
- `leadLimiter` на публичной форме заявок (`src/actions/lead-actions.ts:26`)
- `apiLimiter` на `/api/health`

Работает только in-memory лимитер `src/lib/action-rate-limit.ts` (логин, регистрация, коды почты, Telegram-вход).

*Починка:* либо поднять Redis (можно контейнером рядом, не обязательно Upstash), либо перевести API-роуты на тот же in-memory лимитер, что и actions — он для одного контейнера адекватен.

## 7.2. Главная ошибка выбора: Server Actions как основной транспорт

Это не вкусовщина. Server Action выглядит как обычный вызов функции, и именно поэтому забыть проверку прав легко: нет единой точки, где ставится middleware, нет схемы API, нет HTTP-слоя, который можно протестировать отдельно. Права проверяются руками в каждой из ~170 функций.

Прямое следствие — 8 дыр из раздела 2.3, дыра 2.5 (`getAccessibleStudentIds` — забыли `withAuth` вообще) и обходы бизнес-правил 3.1/3.2 (правило живёт в UI, а action вызывается напрямую).

С tRPC или обычными route handlers + явным middleware центральная точка авторизации была бы по построению.

*Что делать сейчас:* переписывать не надо. Достаточно сделать `roles` **обязательным** параметром `withAuth` (`src/lib/action-utils.ts:3-15`) — тогда пропуск проверки перестанет компилироваться. Это пункт 11 из раздела 5 и он закрывает класс проблем, а не отдельные случаи.

## 7.3. NextAuth v5 beta + неиспользуемый адаптер

`next-auth@^5.0.0-beta.28` — beta в проде. Ломающие изменения между бетами, и именно в её `@auth/core` сейчас критические advisory (2.6).

Отдельно: `@auth/prisma-adapter` **стоит в зависимостях, но не подключен** — в `src/lib/auth.ts` нет `adapter:`, стратегия `jwt` (`:181`). А database sessions закрыли бы находку 2.1 (деактивация не действует 30 дней) бесплатно, без ручной сверки с БД в callback. Сейчас это мёртвая зависимость и упущенное решение.

*Решение:* либо подключить адаптер и `strategy: "database"`, либо оставить JWT, но сверять `isActive`/`role` в callback. Первое проще и надёжнее; второе быстрее по latency.

## 7.4. Next.js для CRM — оправдан, но налог реальный и уже уплачен

CRM — это внутренний инструмент за логином. Всё, ради чего берут Next (SSR, SEO, RSC), нужно здесь только лендингу. Цена видна прямо в коде:

- `src/app/uploads/[...path]/route.ts` — целый роут, чтобы обойти то, что `output: standalone` не раздаёт файлы, загруженные в рантайм
- `src/proxy.ts:37-73` — 35 строк комментариев про то, как Next 16 прогоняет proxy повторно на внутреннем rewrite и как из-за этого получался бесконечный редирект
- `Dockerfile:14` — `--max-old-space-size=2048`, потому что билд берёт до 2 ГБ; на VPS с 956 МБ он не проходит, из-за чего пришлось городить сборку в GitHub Actions с публикацией в GHCR
- `src/actions/telegram-auth-actions.ts:12-18` — отдельный server action ради username бота, потому что `NEXT_PUBLIC_*` вшивается на этапе сборки, а образ собирается без `.env`

Для соло-разработчика один репозиторий, один язык и один деплой — это реальный плюс, который всё перечисленное перевешивает. **Выбор защитим, но он не бесплатный, и счёт уже оплачен.**

## 7.5. Один VPS 956 МБ под всё — впритык, без запаса

`docker-compose.prod.yml`: `db` 256 МБ + `caddy` 128 МБ + `app` 512 МБ = **896 МБ из 956**. Запаса нет. Piston сюда не влезет (см. 7.1) — ему нужно минимум 256-512 МБ плюс tmpfs 256 МБ под джобы.

Нет мониторинга, нет алертов, нет бэкапов БД (ни в CI, ни кроном). При этом `migrate deploy` выполняется на каждом старте контейнера (`docker-entrypoint.sh:8`). Неудачная миграция без бэкапа = потеря данных школы.

Postgres на 256 МБ будет работать, но при росте начнёт активно ходить на диск.

## 7.6. Три формата контента там, где хватило бы одного

- `LessonContentFormat.MARKDOWN` → `src/components/markdown-renderer.tsx` (react-markdown)
- `LessonContentFormat.HTML` → `src/components/html-lesson-renderer.tsx` (iframe-песочница)
- Editor.js JSON для страниц лендинга → `src/app/marketing/[locale]/editor-content.tsx` (ручной рендер с `dangerouslySetInnerHTML`)

Три рендерера, три набора багов, три места для XSS. Editor.js для лендинга школы избыточен: Markdown уже в проекте и покрыл бы задачу без `dangerouslySetInnerHTML` (2.11).
