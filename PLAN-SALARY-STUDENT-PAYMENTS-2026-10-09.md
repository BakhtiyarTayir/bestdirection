# План: поступления от каждого ученика на странице зарплаты — 2026-10-09

Сейчас на странице зарплаты преподавателя (`/salaries/[teacherId]`) у каждой
группы по месяцам видно: учеников, база, ставка, отметки журнала, начислено.
База — одна сумма, и непонятно, из кого она сложилась и кто из учеников
реально заплатил. Добавляем под каждым месяцем группы раскрывающийся список
учеников: сколько начислено, сколько поступило, сколько осталось.

## 0. Решения владельца (2026-10-09) — не пересматривать

- **Только показываем.** Зарплата по-прежнему = процент от НАЧИСЛЕНИЙ
  (`MonthlyCharge`), а не от поступлений (решение 2026-09-20 в силе).
  Формула, заморозка, пересчёт и выплаты не меняются. Поступления —
  справочная колонка рядом.
- **Видит только администратор.** Преподаватель на «Моя зарплата»
  (`/salaries/me`, `GET /salary/me`) ничего нового не получает. Доступ
  проверяется на сервере, а не скрытием кнопки.

## 1. Что показываем

В строке месяца группы — кнопка «Ученики (N)» со стрелкой; по нажатию под
строкой раскрывается таблица:

| Ученик | Начислено за месяц | Поступило за месяц | Осталось |
|---|---|---|---|
| Фамилия Имя (ссылка на карточку `/payments/students/[id]`) | 650 000 | 300 000 | 350 000 (красным) |

- Внизу итог: **«Поступило X из Y (Z %)»**, где Y — сумма начислений
  (совпадает с «Базой» строки).
- Сортировка: сначала с остатком (по убыванию), потом оплатившие.
- «Осталось» < 0 (переплата за месяц) — зелёным как «аванс».
- Ученик, отчисленный после месяца, остаётся в списке закрытого месяца с
  пометкой «отчислен» — деньги за тот месяц его.
- Телефон 360px: таблица прокручивается по горизонтали внутри блока, имя
  переносится.

## 2. Откуда берутся числа (главное — сходимость с «Базой»)

Список учеников строится **тем же путём, что база зарплаты**, иначе сумма
«Начислено» разойдётся с колонкой «База»:

- **Закрытый месяц** — строки `MonthlyCharge` со снимком группы
  (`groupId` = группа единицы, `enrollment.courseId` = курс, `lockedAt` не
  пусто, ученик не удалён) — ровно фильтр `SalaryService.snapshotBase`. Для
  курса без группы — `groupId: null` и тот же курс.
- **Открытый (текущий) месяц** — нынешние записи единицы
  (`loadUnitEnrollments`) и начисление по формуле
  (`ledger.resolveSchedules(...)`, тот же месяц) — как `monthTotals` в
  `unitSchedule`.
- В список попадают ученики с начислением > 0 **или** с поступлением > 0.
- **Поступило за месяц** — оплаты `Payment` (не удалённые) этого ученика по
  этому курсу, у которых `paymentMonth(payment) === month` (т. е. `forMonth`,
  а если он пуст — месяц `paidAt`). Это то же правило, что в долгах
  (`BillingService.computeBillingRows`), поэтому числа согласуются с
  карточкой ученика. Группу платежа не сверяем: долг считается по паре
  «ученик + курс».
- Аванс за следующие месяцы сюда не попадает (он относится к своему месяцу).
- **Расхождение с замороженной базой.** У закрытого месяца база в строке
  зарплаты заморожена (`TeacherSalaryAccrual.base`), а начисления учеников
  могли поправить пересчётом начисления после неё. Если сумма «Начислено»
  ≠ замороженной базе — показать под итогом пометку «база зарплаты
  зафиксирована как N; начисления с тех пор изменились — нажмите
  «Пересчитать»». Не скрывать и не подгонять.

## 3. API

Новый маршрут, только администратор:

`GET /salary/group-students?month=YYYY-MM&groupId=...` (для курса без группы
— `&courseId=...` без `groupId`). Право `manage Salary` (как `overview` в
`salary.controller.ts`). Путь из двух сегментов не пересекается с
`GET /salary/:teacherId`, но маршрут объявить ДО `:teacherId` для
наглядности.

Ответ:
```ts
{
  month: string;
  locked: boolean;            // месяц закрыт
  frozenBase: number | null;  // база из TeacherSalaryAccrual (закрытый месяц), иначе null
  totals: { charged: number; paid: number; remaining: number };
  students: {
    studentId: string; firstName: string; lastName: string;
    unenrolled: boolean;
    charged: number; paid: number; remaining: number;   // remaining = charged - paid
  }[];
}
```

Реализация:
- Метод `SalaryService.groupStudents(query)`; общую часть «единица → записи
  → начисления за месяц» вынести так, чтобы `unitSchedule`/`snapshotBase` и
  новый метод брали учеников ОДНИМ кодом (не копировать фильтры).
- Чистая функция сведения в `domain/salary.ts`:
  `studentPaymentRows(charges, payments, month)` → строки и итоги
  (фильтр «charged > 0 или paid > 0», сортировка, remaining). Тест в
  `salary.spec.ts`.
- Только чтение: заморозку делает уже существующая ленивая логика
  (`resolveSchedules`), новых записей маршрут сам не создаёт.
- Месяц невалидный — 400; группа/курс не найдены — 404.

## 4. Web

- `src/lib/api/salary.ts` — тип `ApiSalaryGroupStudents` и
  `getSalaryGroupStudents(month, groupId, courseId)`.
- `teacher-salary-view.tsx`: в строке месяца кнопка «Ученики (N)» (N =
  `row.studentsCount`); по раскрытию — загрузка списка (один запрос на
  раскрытие, кэш в состоянии компонента), затем подтаблица под строкой
  (`Fragment` + строка на всю ширину). Пока грузится — «Загрузка…», ошибка
  — текст ошибки.
- `my-salary-view.tsx` (страница преподавателя) **не трогать**.
- Переводы ru и uz (латиница) в namespace страницы зарплат; JSON править без
  переформатирования файла.

## 5. Тесты (e2e `api/test/salary.e2e-spec.ts`, свои данные)

1. ADMIN — 200; TEACHER — 403 даже на свою группу; аноним — 401.
2. Сумма `charged` по ученикам == база месяца у владельца группы — для
   открытого и для закрытого месяца.
3. Оплата с `forMonth` этого месяца учитывается; с другим `forMonth` — нет;
   без `forMonth` — по месяцу `paidAt`; удалённая (`deletedAt`) — нет.
4. Переведённый ученик: закрытый месяц — в прежней группе (по снимку), в
   новой его нет; текущий месяц — в новой.
5. Отчисленный после месяца — есть в закрытом месяце с `unenrolled: true`.
6. Ученик без начисления, но с оплатой за месяц — в списке (charged 0).
7. Unit-тест `studentPaymentRows`: итоги, сортировка, переплата.

## 6. Порядок работы

1. `middle`: API + доменная функция + тесты; `cd api && npm test` зелёный.
2. Проверка ведущим (дифф, сходимость с базой, права).
3. `middle`: web.
4. Проверка ведущим, затем `git-agent`: два коммита
   (`feat(salary): поступления по ученикам в месяце группы (api)`,
   `feat(salaries): список учеников с оплатами на странице зарплаты`), пуш по
   команде владельца.

## 7. Вне плана

- Зарплата от поступлений — не делаем (решение владельца).
- Преподаватель свои поступления не видит.
- Отдельный отчёт «собираемость по группам» — можно позже на основе того же
  маршрута.
