## 2. Порядок этапов и почему он такой

Владелец перечислил задачи в порядке «зарплаты → профиль → филиалы». Делать их предлагается в обратном порядке:

```
Этап 1. Филиалы      → Этап 2. Профиль пользователя  → Этап 3. Зарплаты
(справочник + поля)     (логин вместо почты, филиал,    (строке зарплаты нужен
                         запись на курс)                 снимок филиала)
```

Причина простая: филиал — самое широкое, но самое мелкое изменение, и он попадает в обе оставшиеся задачи. Если сделать зарплаты первыми, строки начислений зарплаты придётся мигрировать второй раз, чтобы добавить в них филиал, а форму создания ученика — переделывать дважды. Обратный порядок экономит две миграции и одну переделку формы.

Каждый этап самостоятелен: после любого из них система рабочая и деплоится.

## 3. Этап 1. Филиалы

### 3.1. Что такое филиал в этой предметной области

Филиал — физическая точка учебного центра: адрес, где идут занятия, и касса, куда несут деньги. Из этого следует, что филиал — свойство **группы** (группа занимается в конкретном здании), а не курса: курс «Python для школьников» — это программа, и её одинаково ведут в трёх филиалах.

Ученик и преподаватель приписаны к филиалу для удобства: списки, фильтры, SMS-рассылки. Их приписка — справочная, потому что настоящая привязка идёт через группу.

### 3.2. Три возможных реализации

| Вариант | Что это | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| **А. Строка или enum в `Group`** | Поле `branch String?` с названием | Одна миграция, полчаса работы | Опечатки («Чиланзар» и «чиланзар» — два филиала), нет адреса и телефона, нет фильтра по справочнику, переименование правит все строки | Отклонён |
| **Б. Справочник `Branch` + `branchId`** | Отдельная таблица, ссылки из `Group`, `User`, `Payment` | Фильтры, отчёты по филиалам, адрес и телефон в одном месте, задел под права | Одна миграция с переносом данных, правки в формах и списках | **Выбран** |
| **В. Мультиарендность (tenant)** | Изоляция данных по арендатору на уровне каждого запроса | Настоящая независимость филиалов | Это другой продукт; в `MIGRATION-NESTJS.md`, раздел «Не цели», мультиарендность прямо исключена и вынесена в `~/Projects/saas-crm` | Отклонён |

### 3.3. Куда ставить `branchId`

| Сущность | Решение | Почему |
|---|---|---|
| `Group` | **Да, обязательно** (`branchId String`, `NOT NULL`) | Носитель смысла: группа занимается в конкретном филиале. Обязательность — решение владельца; она же позволяет сделать имя группы уникальным внутри филиала |
| `User` | **Да**, `branchId String?`; обязательно в форме создания | Приписка ученика и преподавателя: списки, фильтры, «свои» для администратора в будущем. В базе колонка необязательная — см. ловушку 3.8.3 |
| `Payment` | **Да**, снимком при создании | Касса филиала. Выводить через группу нельзя: `Payment.groupId` необязателен и обнуляется при удалении группы (`onDelete: SetNull`), а отчёт по кассе за прошлый год после этого поехал бы |
| `Course` | **Нет** (разобрано ниже) | Курс — программа, а не место. Один курс ведут в нескольких филиалах |
| `AttendanceSession` | **Нет** | Выводится через группу, собственное поле только добавит рассинхрон |
| `TeacherSalaryAccrual` (этап 3) | **Да**, снимком | По той же причине, что у `Payment`: отчёт «зарплаты по филиалу за март» не должен меняться от перевода группы |
| `Enrollment` | **Нет** | Филиал ученика определяется его группой; дублировать не нужно |

**Почему курс не привязывается к филиалу (вопрос владельца от 2026-09-20).** Курс здесь — не «направление», а контейнер с содержимым: на `courseId` висят уроки, тесты, экзамены, домашние задания и прогресс учеников (`Lesson`, `Assessment`, `Homework`, `LessonProgress`). Обязательная привязка курса к филиалу означает, что одна программа в двух филиалах — это два курса с двумя комплектами уроков. Последствия:

- правку урока или теста надо повторять в каждой копии, синхронизации между ними в системе нет (`copiedFromId` фиксирует происхождение, но не связывает содержимое);
- сквозная статистика по программе перестаёт считаться;
- на публичном лендинге появляются два одинаковых курса — у каждого свои `isPublicListed`, `price`, `intakeStartDate`;
- ученик, перешедший в другой филиал, теряет пройденные уроки и результаты тестов: это другой курс, историю туда не перенести;
- возникает второй источник правды — филиал у группы и филиал у её курса, и весь код обязан следить за их совпадением.

При этом всё, ради чего обычно хотят привязку, уже решается группой: цена (`Group.price` важнее `Course.price`), преподаватель (`Group.teacherId` важнее `Course.teacherId`), расписание. Если понадобится скрыть чужие курсы из форм, есть два способа без дублирования содержимого: фильтр «курсы, где есть мои группы» (вычисляется, поле не нужно) или связка многие-ко-многим «курс предлагается в филиалах X, Y» при одном комплекте уроков.

### 3.4. Схема

```prisma
/// Филиал учебного центра: адрес, где идут занятия, и касса, куда несут деньги.
/// Филиал — свойство группы, а не курса: одну программу ведут в нескольких
/// филиалах. У ученика и преподавателя филиал справочный, настоящая привязка
/// идёт через группу.
model Branch {
  id        String   @id @default(cuid())
  name      String   @unique
  address   String?
  phone     String?
  // Выключенный филиал не предлагается в формах, но его история остаётся
  isActive  Boolean  @default(true)
  sortOrder Int      @default(0)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  groups   Group[]
  users    User[]
  payments Payment[]

  @@index([isActive])
}
```

Добавляется в существующие модели:

```prisma
model Group {
  // …
  // Обязателен: группа всегда занимается в конкретном филиале
  branchId String
  branch   Branch @relation(fields: [branchId], references: [id], onDelete: Restrict)

  // Имя уникально внутри филиала, а не на весь центр: «Python-1» есть
  // в каждом филиале, и это нормально. Работает только потому, что
  // branchId обязателен — с NULL Postgres пропустил бы дубликаты
  @@unique([courseId, branchId, name])
  @@index([branchId])
}

model User {
  // …
  // В форме создания обязателен, в базе — нет: пользователя заводит ещё и
  // вход через Telegram (AuthService.findOrCreateTelegramUser), где филиала
  // неоткуда взять
  branchId String?
  branch   Branch? @relation(fields: [branchId], references: [id], onDelete: SetNull)
  @@index([branchId])
}

model Payment {
  // …
  // Снимок на момент приёма денег: группу могут перевести в другой филиал
  // или удалить, а касса за закрытый месяц меняться не должна
  branchId String?
  branch   Branch? @relation(fields: [branchId], references: [id], onDelete: SetNull)
  @@index([branchId])
}
```

**Почему `onDelete: Restrict` у группы, а не `SetNull`.** Удаление филиала, в котором есть группы, — почти всегда ошибка. `Restrict` превращает её в понятную ошибку вместо тихой потери привязки у десятка групп. Для выхода из положения есть `isActive: false`.

**Почему `Branch` не попадает в мягкое удаление.** Набор `SOFT_DELETE_MODELS` (`api/src/common/prisma/prisma.service.ts:7`) — это `User`, `Course`, `Lesson`, и каждый элемент в нём стоит дорого: удалённые записи невидимы обычному клиенту, и весь код, которому они нужны, обязан идти через `prismaUnscoped`. Филиалов будет два-три, для них достаточно `isActive`.

**Про обязательность.** У группы `branchId` становится `NOT NULL` — но не одним движением: миграция сначала добавляет колонку, заполняет её и только потом ставит ограничение (раздел 3.5). У пользователя колонка остаётся необязательной, а обязательность живёт в схеме формы создания: пользователей заводит не только администратор.

### 3.5. Миграция данных

Одним файлом миграции, сразу после `CREATE TABLE`:

```sql
INSERT INTO "Branch" ("id", "name", "isActive", "sortOrder", "createdAt", "updatedAt")
VALUES ('branch_main', 'Главный', true, 0, NOW(), NOW());

UPDATE "Group"   SET "branchId" = 'branch_main';
UPDATE "User"    SET "branchId" = 'branch_main';
UPDATE "Payment" SET "branchId" = 'branch_main';

-- Только теперь, когда пустых значений не осталось
ALTER TABLE "Group" ALTER COLUMN "branchId" SET NOT NULL;

-- Имя группы уникально внутри филиала, а не на весь центр
DROP INDEX "Group_courseId_name_key";
CREATE UNIQUE INDEX "Group_courseId_branchId_name_key"
  ON "Group" ("courseId", "branchId", "name");
```

**Порядок внутри файла важен.** `SET NOT NULL` до `UPDATE` уронит миграцию на живой базе, а `prisma migrate` не умеет откатываться — контейнер `api` просто не поднимется. Поэтому миграция пишется руками, а не генерируется целиком.

Название «Главный» администратор переименует в интерфейсе. Данных мало (прод: база 11 МБ), `UPDATE` без `WHERE` безопасен и быстр.

Миграции накатываются автоматически при старте контейнера `api` — отдельного шага деплоя не нужно; перед деплоем CI делает бэкап (`scripts/backup/backup-db.sh`).

### 3.8. Ловушки этапа

1. **Уникальность имени группы — решено.** Было `@@unique([courseId, name])` (`prisma/schema.prisma:440`), то есть «Python-1» на весь центр одна. Владелец выбрал обязательный филиал у группы, поэтому ключ становится `[courseId, branchId, name]` и одинаковые имена в разных филиалах разрешены. Это работает **только** при `NOT NULL`: с `NULL` в ключе Postgres пропустил бы дубликаты — та же грабля, что закрывал частичный индекс `20260916090000_attendance_no_group_unique`. Проверить перед миграцией: `GroupsService.update` ищет тёзку по `courseId_name` (`groups.service.ts:117`) — запрос надо переписать на новый составной ключ, иначе он просто перестанет компилироваться.
2. **Мягкое удаление у `User`.** Любая выборка пользователей по филиалу через обычный `prisma` не видит удалённых. Для отчётов, где нужны и они, — `prismaUnscoped` (`api/src/common/prisma/prisma.service.ts`).
3. **Фильтр по филиалу в биллинге идёт через группу.** У записи `Enrollment` своего филиала нет, поэтому фильтр должника — `{ group: { is: { branchId } } }`. Записи **без группы** при включённом фильтре выпадут из списка. Это не баг, но в интерфейсе нужна строчка «без группы: N» — точно как уже сделано для `withoutGroup` в `billing.service.ts:107`.
4. **SMS-рассылки** (`SmsBroadcast` привязан к группе) фильтр по филиалу получают бесплатно через группу; отдельной работы не требуют.
5. **Фильтр по филиалу считается через группы, а не через поле пользователя.** Ученик может ходить на английский в одном филиале и на программирование в другом — поле `User.branchId` у него одно, «основное». Если фильтр списка учеников будет смотреть только на это поле, такой ученик пропадёт из выборки второго филиала. Правило: фильтр везде идёт через группы (`{ enrollments: { some: { group: { is: { branchId } } } } }`), а `User.branchId` используется для показа и для тех, у кого групп ещё нет.
6. **Пользователи без филиала всё равно появятся.** `AuthService.findOrCreateTelegramUser` (`auth.service.ts:341`) заводит пользователя при первом входе через Telegram — филиала там нет. В списках такие должны попадать в «без филиала», а не исчезать.

## 4. Этап 2. Профиль пользователя: логин вместо почты, филиал, запись на курс

Три изменения в одном экране создания пользователя. Логин идёт первым: он трогает вход в систему, и остальное делается поверх него.

### 4.1. Логин вместо почты

#### Как сейчас

Почта — единственный опознавательный знак человека в системе:

| Что делает почта | Где |
|---|---|
| Вход по паролю | `api/src/modules/auth/auth.service.ts:58` (`loginWithPassword`), страница `src/app/[locale]/(auth)/login` |
| Самостоятельная регистрация с кодом на почту | `auth.service.ts:157`…`:203`, модель `EmailVerificationCode`, страница `(auth)/register` |
| Восстановление пароля кодом на почту | `auth.service.ts:205`…`:240`, страница `(auth)/forgot-password` |
| Уникальность пользователя | `User.email @unique`, `UsersService.emailTakenBy` (`users.service.ts:342`) |
| Показ в списках | `~20` экранов: `users/user-list.tsx`, `students`, `teachers`, `audit-table.tsx`, домашние задания, состав группы |

Почта уже сейчас необязательна (`email String?`, `prisma/schema.prisma:131`) — офлайн-учеников заводят без неё. Но тогда такой ученик **не может войти паролем**: подставлять в форму входа нечего. Остаётся только Telegram, и то если он привязан. Именно это и чинится.

#### Что становится

```prisma
model User {
  // Было: email String? @unique
  // Логин — единственный опознавательный знак при входе. Почты у учеников
  // в Узбекистане часто нет вовсе, а без неё прежний вход был невозможен.
  // Хранится в нижнем регистре: иначе «Ivanov» и «ivanov» — разные люди.
  login String @unique
  // …
}
```

Модель `EmailVerificationCode` удаляется, `api/src/common/email/` (`EmailService`, `codes.ts`) — тоже, вместе с переменными SMTP в окружении.

**Формат логина:** `^[a-z0-9][a-z0-9._-]{2,29}$` — латиница, цифры, точка, дефис, подчёркивание; 3–30 символов; приводится к нижнему регистру на входе.

#### Генерация

Генерирует **сервер**, а не браузер: свободен ли логин, знает только база.

```
POST /users/login-suggestion { firstName, lastName } → { login: "ivan.ivanov" }
```

Внутри — уже готовые `slugify` и `generateUniqueSlug` из `api/src/common/slugify.ts`: пакет `transliteration` переводит кириллицу («Иван Иванов» → `ivan.ivanov`), узбекская латиница проходит как есть. Занятое имя получает суффикс: `ivan.ivanov2`, `ivan.ivanov3`. Проверка занятости идёт через `prismaUnscoped` — по той же причине, по которой так устроен `emailTakenBy`: уникальный индекс не знает про мягкое удаление, и логин удалённого пользователя остаётся занятым.

В форме: логин подставляется сам, как только заполнены имя и фамилия, рядом кнопка «Сгенерировать». Как только администратор правит поле руками, автоподстановка выключается — иначе она затрёт введённое при следующем изменении фамилии. Занятость проверяется живьём (`GET /users/login-available?login=`) и ещё раз при сохранении — между проверкой и вставкой логин мог занять другой администратор, это уже разобранная в `users.service.ts:88` гонка.

#### Пароль

Пароль обязателен и сейчас (`passwordSchema`, минимум 8 символов) — это не меняется. Добавляется практичное: кнопка «Сгенерировать пароль» и показ сгенерированного пароля **один раз** после создания, чтобы администратор мог выдать его ученику. Повторно посмотреть пароль нельзя — в базе лежит только хэш.

#### Что умирает вместе с почтой и чем заменяется

| Механизм | Замена |
|---|---|
| Самостоятельная регистрация `/register` | **Убрать страницу.** Учеников заводит администратор; заявки с лендинга идут в `CourseLead`, заявки на курс — в `EnrollmentRequest`. Для офлайн-центра самозапись по почте всё равно не работала |
| Восстановление пароля `/forgot-password` | **Два пути вместо почты** — администратор и сам пользователь через Telegram. Разобрано ниже |
| Вход тех, кто забыл пароль | **Telegram-вход** остаётся как был и почты не требует (`auth.service.ts:77`, `:92`) |

#### Сброс пароля без почты (решение владельца 2026-09-20)

**Путь 1. Администратор задаёт новый пароль.** Такой возможности сейчас нет вовсе: `updateUserSchema` (`api/src/modules/users/dto/user.dto.ts`) пароля не содержит. Добавляется поле `password` в `PATCH /users/:id` (только ADMIN); после смены — `sessionUsers.forget(id)` и `sessions.destroyAllFor(id)`, как уже делается при деактивации (`users.service.ts:185`).

**Путь 2. Пользователь сам, через Telegram.** Работает, если Telegram привязан (`User.telegramChatId`):

```
Страница входа, «Забыли пароль?»
  → вводит ЛОГИН
  → сервер находит пользователя и его telegramChatId
  → TelegramNotifyService.send(chatId, "Код для смены пароля: 123456")
  → пользователь вводит код и новый пароль
  → пароль меняется, ВСЕ прежние сессии завершаются
```

Ход повторяет нынешний почтовый один в один (`auth.service.ts:205`…`:238`) — меняется только транспорт, вместо `EmailService` берётся уже готовый `TelegramNotifyService.send` (`api/src/common/telegram/telegram-notify.service.ts:14`). Сохраняются оба защитных свойства, которые там уже есть: неизвестный или выключенный логин получает такой же нейтральный ответ `{ ok: true }` (иначе форма превращается в перебор логинов), а успешная смена обрывает все сессии — если доступ был у чужого, он потерян.

Таблица кодов переезжает с почты на пользователя:

```prisma
/// Код смены пароля, отправленный в Telegram. Заменяет EmailVerificationCode:
/// адреса больше нет, код принадлежит пользователю.
/// В базе лежит хэш — утечка таблицы не даёт сменить чужой пароль.
model PasswordResetRequest {
  id        String   @id @default(cuid())
  userId    String   @unique
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  codeHash  String
  attempts  Int      @default(0)
  expiresAt DateTime
  sentAt    DateTime @default(now())
}
```

Константы (15 минут жизни, не больше 5 попыток, повтор не чаще раза в минуту) переезжают из `api/src/common/email/codes.ts` в `api/src/common/auth/`; в хэш вместо адреса входит `userId`. Маршруты публичные, поэтому на них обязателен лимит частоты — `@nestjs/throttler` уже подключён.

**Путь 3. Код по SMS — отложен (решение владельца 2026-09-20: пока не включаем).** Раздел ниже сохранён как заготовка на будущее. Eskiz подключён и работает (`api/src/common/sms/eskiz.service.ts`), ход сброса тот же, меняется только транспорт. Но перед включением надо решить вопрос, которого у почты не было: **чей это телефон**.

#### Чей номер у ученика (вопрос владельца 2026-09-20)

Владелец верно заметил: у ученика может не быть своего телефона, номер есть только у родителей. Проверка кода показала, что **отдельное поле «телефон родителя» заводить не нужно — оно уже есть, только в правильном месте**:

| Что | Где уже лежит |
|---|---|
| Свой телефон ученика | `User.phone` — поле есть у каждого пользователя и **уже правится в профиле** (`updateProfileSchema`, `profile-form.tsx:177`). Добавлять нечего |
| Телефон родителя | `User.phone` **родителя**: родитель — отдельный пользователь с ролью `PARENT`, связанный через `ParentStudent` |
| Кому из родителей звонить и слать первым | `ParentStudent.isPrimary` — признак заведён ровно для этого (`prisma/schema.prisma:191`) |

Родителя завести дёшево: диалог в карточке ученика просит только имя, фамилию и телефон, пароль генерируется случайным, почта необязательна (`parents.service.ts:167`…`:185`, интерфейс — `src/components/parents-panel.tsx`). Никакой регистрации родителю проходить не надо.

И главное: **SMS-рассылки в системе уже идут родителям, а не ученикам** — план рассылки строится по `parents.groupRecipients(groupId)`, то есть по родителям учеников группы с их номерами (`sms.service.ts:399`…`:435`). Канал «написать взрослому» построен и проверен.

**Правило выбора получателя для кода сброса:**

```
свой телефон (User.phone)  →  телефон ОСНОВНОГО родителя (isPrimary)  →  нет канала: к администратору
```

На экране обязательно показывать, **на чей номер ушёл код**, маской: «Код отправлен на +998 ** *** ** 67 (мама)». Иначе ученик будет ждать SMS, которая пришла родителю, и решит, что сброс сломан.

**Решение, которое надо принять осознанно:** код доступа к учётной записи ребёнка уходит взрослому. Для детского учебного центра это нормально и даже правильно — родитель и есть ответственный за ребёнка. Но записать это надо явно, а не получить случайно.

#### Разовая чистка данных перед включением SMS-сброса

Сегодня у `User.phone` ученика **нет определённого смысла**: администраторы вписывали туда и собственный номер ребёнка, и родительский — различить их системе нечем. После введения правила выше номер ученика начинает означать «его собственный», и старые данные этому не соответствуют.

Поэтому перед включением пути 3:

1. Подпись поля в профиле и в форме пользователя меняется на «Свой номер» с пояснением «номер родителя указывается в карточке родителя».
2. Администратор проходит по ученикам и переносит родительские номера туда, где им место — в карточку родителя. Автоматически это не определить: номер ребёнка и номер матери выглядят одинаково.
3. Пока чистка не сделана, путь 3 включать нельзя — иначе код уйдёт «ученику» на номер, который на самом деле родительский, и в журнале SMS это будет выглядеть как сообщение ученику.

**Побочная польза.** Родителей заводят со случайным паролем, и войти они сегодня могут только через Telegram (`parents.service.ts:169`). После удаления почты у них не остаётся и восстановления — SMS-сброс на их собственный номер закрывает эту дыру заодно.

#### Миграция — обязательно в два шага

Одношаговая замена оставит без входа всех, кто сегодня заходит по почте, включая владельца. Поэтому:

**Шаг 1 (деплой A).** Колонка `login` добавляется необязательной и заполняется:

```sql
ALTER TABLE "User" ADD COLUMN "login" TEXT;
-- Локальная часть почты, приведённая к формату логина
UPDATE "User" SET "login" = lower(split_part("email", '@', 1)) WHERE "email" IS NOT NULL;
-- Остальным логин генерирует скрипт миграции из имени и фамилии,
-- он же разводит коллизии суффиксами
```

Вход в этот момент принимает **и логин, и почту** — старые пароли и привычки работают. Форма и списки уже показывают логин.

**Шаг 2 (деплой B, через несколько дней).** `login` становится `NOT NULL @unique`, колонка `email` и таблица `EmailVerificationCode` удаляются, вход по почте убирается из `loginWithPassword`.

Перед шагом 1 выгрузить список «кто теперь под каким логином» и отдать владельцу — людям надо сказать, чем они теперь входят. Проверить, что у администратора логин есть и он работает, **до** удаления почты.

#### Ловушки

1. **Регистр и пробелы.** Приводить к нижнему регистру и обрезать пробелы на входе в DTO, а не в сервисе, иначе «Ivanov » создаст второго человека.
2. **`prismaUnscoped` при проверке занятости** — логин держит занятым и мягко удалённый пользователь (`users.service.ts:342`).
3. **`SessionUser.email`** (`api/src/common/auth/session-user.ts`) меняется на `login`; потребители — `session-user.cache.ts`, `auth.service.ts:246`, весь `web`, который показывает почту в шапке.
4. **`prisma/seed.ts:12`** создаёт `admin@lms.com`, `teacher@lms.com`, `student@lms.com` — переписать на логины, иначе тесты и локальная разработка встанут.
5. **~20 экранов показывают почту** — механическая, но обязательная замена; `grep -rln "email" src --include=*.tsx` даёт полный список.
6. **Телефон логин не заменяет.** Он остаётся необязательным и неуникальным: у двух детей из одной семьи часто один родительский номер.

#### Страница входа после изменений

Сейчас (`src/app/[locale]/(auth)/login`): кнопка «Telegram orqali kirish», разделитель «YOKI», поля **Email** и **Parol**, ссылка «Parolni unutdingizmi?», кнопка «Kirish» и внизу «Akkauntingiz yo'qmi? Ro'yxatdan o'tish».

| Элемент | Что с ним делаем |
|---|---|
| Кнопка входа через Telegram | **Не трогаем.** Работает как работала |
| Поле **Email** | → **Login**. Тип поля обычный текстовый, без проверки на адрес; значение приводится к нижнему регистру |
| Поле **Parol** | Без изменений |
| «Parolni unutdingizmi?» | Ведёт на сброс: вводится **логин**, код приходит в Telegram (путь 2 раздела «Сброс пароля без почты») |
| «Ro'yxatdan o'tish» | **Убирается совсем** — самостоятельная регистрация закрыта, учеников заводит администратор |

#### Два пути входа независимы — и это ответ на вопрос «как войти в следующий раз»

Вход через Telegram **никогда не спрашивает ни логин, ни пароль**: бот подтверждает личность, сервер находит пользователя по `telegramChatId` и открывает сессию (`auth.service.ts:77`, `:92`). Поэтому человек, вошедший через Telegram, в следующий раз просто снова жмёт ту же кнопку. Ничего не меняется ни сейчас, ни после удаления почты.

Логин с паролем — **второй, независимый путь к той же учётной записи**. Кто чем пользуется:

| Кто | Чем входит |
|---|---|
| Ученик, заведённый администратором | Логином и паролем, которые выдал администратор. Дополнительно может привязать Telegram и дальше входить одной кнопкой |
| Ученик, впервые пришедший через Telegram | Только Telegram. Пароля у него нет вовсе (`passwordHash` пуст), и попытка войти паролем корректно отвергается — `loginWithPassword` отдельно проверяет `!user.passwordHash` (`auth.service.ts:66`) |
| Родитель | Заводится со случайным паролем, которого не знает: только Telegram, а после этапа — ещё и сброс пароля |
| Администратор, преподаватель | Логином и паролем |

Один человек может пользоваться обоими путями: это одна учётная запись, а не две.

#### Что обязательно чинится во входе через Telegram

Миграция обнажает два места в `findOrCreateTelegramUser` (`auth.service.ts:341`).

**1. Пользователь создаётся без логина — после `NOT NULL` этот `create` упадёт.** Сейчас он заполняет только имя, фамилию, роль и Telegram-поля; ни почты, ни пароля там нет. Логин надо генерировать тут же — из имени пользователя Telegram, иначе из имени и фамилии, теми же `slugify` + `generateUniqueSlug`. Без этой правки вход через Telegram сломается ровно в день второго деплоя.

**2. Вход через Telegram сейчас заводит учётную запись ЛЮБОМУ.** Незнакомый `telegramChatId` молча создаёт нового пользователя с ролью `STUDENT` — без филиала, без записи на курс, без пароля. Пока открыта страница регистрации, это лишь ещё одна дверь; **после её закрытия это остаётся единственной открытой дверью в систему**, и она противоречит принятому решению «учеников заводит администратор».

Предлагается закрыть в этом же этапе: вход через Telegram пускает только тех, у кого `telegramChatId` уже привязан (то есть человек завёлся у администратора и сам привязал Telegram в профиле). Незнакомцу — понятный ответ «обратитесь к администратору центра», без создания записи. Создание пользователя из `findOrCreateTelegramUser` убирается, остаётся только поиск.

Побочный эффект, о котором надо знать: те, кто уже завёлся через Telegram таким образом, в базе останутся и входить продолжат — правило касается только новых.

**Страница регистрации исчезает целиком, без остатка.** Сегодня `Ro'yxatdan o'tish` состоит ровно из двух путей: кнопка «Telegram orqali kirish» и поле Email с кнопкой «Pochtaga kod olish». Почта уходит вместе с колонкой, а кнопка Telegram на этой странице — это и есть та самая открытая дверь из пункта 2: она ведёт в `findOrCreateTelegramUser`, который заводит учётную запись незнакомцу. После обеих правок на странице не остаётся ни одного работающего элемента, поэтому она удаляется, а ссылки на неё со страницы входа снимаются.

### 4.2. Профиль пользователя: логин, Telegram и кнопка «Написать»

#### Свой профиль (`/profile`)

Сейчас страница показывает имя, фамилию, телефон и почту (`src/app/[locale]/(dashboard)/profile/page.tsx`, `profile-form.tsx`) плюс блок привязки Telegram (`src/components/telegram-link.tsx`). После этапа она показывает:

| Что | Поведение |
|---|---|
| **Логин** | Виден всегда — человек должен знать, чем он входит. Только для чтения: менять логин может администратор в карточке пользователя. Смена логина обрывает привычный вход, и делать её между делом не стоит |
| **Telegram** | Статус привязки и имя пользователя (`@ivanov`) — оба уже приходят из `GET /me/telegram` (`telegram-link.service.ts:status`) |
| **Привязать / отвязать Telegram** | Уже работает: кнопка выдаёт одноразовый код и открывает бота по ссылке `t.me/<бот>?start=<код>`, статус опрашивается, пока привязка не произойдёт (`telegram-link.tsx:56`…`:90`). Трогать не нужно — но после отказа от почты это **единственный** способ самому восстановить доступ, поэтому в блоке нужна поясняющая строка: «привяжите Telegram, чтобы сбрасывать пароль без администратора» |
| **Телефон** | Поле уже есть и уже правится самим пользователем (`profile-form.tsx:177`). Меняется только подпись: «Свой номер», с пояснением, что номер родителя живёт в карточке родителя |
| **Сменить пароль** | Как сейчас, со старым паролем (`POST /me/password`) |

Почта со страницы исчезает вместе с колонкой.

#### Карточка другого человека и списки: кнопка «Написать в Telegram»

Писать самому себе незачем, поэтому кнопка живёт не в своём профиле, а там, где администратор или преподаватель смотрит на **другого** человека:

- `/users/[userId]` — карточка пользователя;
- `/payments/debtors` — список должников (данные уже есть: `telegramUsername` приходит в каждой строке, см. `ApiBillingRow` в `src/lib/api/billing.ts`);
- `/payments/students/[studentId]` — карточка биллинга ученика;
- состав группы (`src/components/groups/group-students-manager.tsx`).

Кнопка — обычная ссылка `https://t.me/<telegramUsername>`, открывается в новой вкладке и перебрасывает в приложение Telegram. Отдельного кода на сервере не требует: `telegramUsername` уже хранится в `User` и уже отдаётся в нескольких ответах; где не отдаётся — добавляется в `select`.

**Ловушка: имя пользователя в Telegram необязательно.** Человек может быть привязан (`telegramChatId` есть), но `telegramUsername` быть пустым — в Telegram это допустимо. Тогда прямой ссылки не существует, и кнопку надо **прятать, а не показывать неработающей**. Писать такому человеку может только бот — это отдельная задача (уведомления через бота уже есть в `TelegramNotifyService`), и её стоит рассмотреть, если пустых имён окажется много.

**Ловушка: имя пользователя меняется.** Telegram позволяет сменить `@имя` в любой момент, а в базе оно записано в момент привязки и само не обновляется. Ссылка на старое имя ведёт в никуда. Обновлять его нужно при каждом взаимодействии с ботом — это правка в обработчике бота, не в интерфейсе.

### 4.3. Филиал в форме создания

Поле «Филиал» обязательно (решение владельца). Оно же управляет остальной формой: выбранный филиал сужает список групп в блоке «Обучение» — иначе администратор ищет нужную «Python-1» среди одноимённых групп всех филиалов.

Обязательность живёт в схеме формы и в `createUserSchema`, но не в колонке: пользователей заводит ещё и вход через Telegram (`auth.service.ts:341`), где филиала неоткуда взять.

### 4.4. Запись на курс прямо при создании

Сегодня, чтобы завести ученика с обучением и ценой, администратор проходит **три разных экрана**:

1. `/users/new` — создать пользователя (`create-user-form.tsx` → `users.service.ts:69`).
2. `/groups/…` или `/courses/…` — записать на курс и в группу (`groups.service.ts:192`, `courses.service.ts:240`).
3. `/payments/students/[studentId]` — задать цену и дату начала (`billing.service.ts:186`).

Между шагами данные не связаны: ученик, созданный на шаге 1, без шагов 2–3 не существует для биллинга вообще.

Форма `/users/new` при роли `STUDENT` получает блок «Обучение»:

| Поле | Значение по умолчанию | Обязательное |
|---|---|---|
| Курс | список курсов, не в Корзине | да, если блок заполняется |
| Группа | группы выбранного курса **в выбранном филиале** | нет (можно записать на курс без группы) |
| Цена в месяц | цена группы, иначе цена курса — как `priceFor` (`domain/billing.ts:165`) | нет; пусто = «как у группы» |
| Дата начала обучения | сегодня | нет; пусто = дата создания |
| Начисление за первый неполный месяц | подсказка сервера `suggestedFirstMonthCharge` (`billing.service.ts:123`) | нет |

Весь блок необязателен: преподавателя или ученика «на будущее» заводят, не трогая его.

### 4.5. Контракт API

Расширяется существующий `POST /users` — отдельного маршрута не нужно:

```ts
// api/src/modules/users/dto/user.dto.ts
export const createUserSchema = z.object({
  login: z.string().trim().toLowerCase().regex(/^[a-z0-9][a-z0-9._-]{2,29}$/, "loginInvalid"),
  password: passwordSchema,          // обязателен, как и был
  firstName: nameSchema,
  lastName: nameSchema,
  phone: phoneSchema,
  role: roleSchema,
  branchId: z.string().min(1, "branchRequired").max(40),
  // Блок «Обучение». Разрешён только для роли STUDENT — проверяется
  // в superRefine, а не в сервисе: ошибка должна прийти как 400 с полем
  enrollment: z
    .object({
      courseId: z.string().min(1, "courseRequired").max(40),
      groupId: z.string().max(40).optional(),
      priceOverride: z.number().int().positive("amountPositive").max(1_000_000_000).optional(),
      // Календарная дата строкой: Date уехал бы на сутки при UTC-сериализации
      startsAt: z.string().regex(/^\d{4}-\d{2}-\d{2}$/, "invalidDate").optional(),
      firstMonthCharge: z.number().int().min(0).max(1_000_000_000).optional(),

    .optional(),
});
```

Ответ дополняется `enrollmentId`, чтобы форма могла сразу увести администратора на карточку биллинга ученика.

### 4.6. Транзакция

`UsersService.create` оборачивается в `prisma.$transaction`: пользователь и запись на курс создаются вместе или не создаются вовсе. Без транзакции падение второго шага оставляет ученика без обучения — ровно ту дыру, которую этап и закрывает.

Зависимость модулей: `UsersModule` импортирует `BillingModule` (он уже экспортирует `BillingLedgerService`, `billing.module.ts:12`). Цикла не возникает: биллинг про пользователей ничего не знает. Проверки «группа принадлежит курсу», «группа в выбранном филиале», «курс не в Корзине», «роль STUDENT» делаются перед транзакцией.

Заморозка закрытых месяцев здесь **не нужна**: запись новая, прошлого у неё нет.

### 4.7. Ловушки этапа

1. **`@@unique([studentId, courseId])`** у `Enrollment` (`prisma/schema.prisma:361`) — повторная запись на тот же курс невозможна. Для нового пользователя конфликта быть не может, но код должен отдавать `alreadyEnrolled`, а не 500, если форму отправили дважды.
2. **Дата начала.** Только строкой `YYYY-MM-DD` и через `toNoonUtc` (`api/src/common/date-only.ts`). Прямой `Date` из формы в UTC+5 приедет вчерашним днём — этот урок уже оплачен проектом, см. комментарий в `dto/group.dto.ts`.
3. **Цена в поле «цена в месяц» — это `priceOverride`, личная цена ученика.** Она перебивает цену группы навсегда, в том числе после подорожания группы. Если администратор имел в виду «как у всех», поле надо оставить пустым — подпись под полем обязана это объяснять.
4. **Роль меняется в форме.** Переключение `STUDENT → TEACHER` должно скрывать и очищать блок «Обучение», иначе в теле запроса уедет `enrollment` при роли `TEACHER` и вернётся 400.
5. **Форма правки пользователя блок «Обучение» не получает.** Условия обучения уже правятся на `/payments/students/[studentId]`, дублировать их в двух местах — верный способ развести две разные правды. В карточке `/users/[userId]` достаточно показать курс, группу и цену со ссылкой на карточку биллинга.

## 5. Этап 3. Зарплаты преподавателей

### 5.1. Формула

Для пары «преподаватель + группа» за календарный месяц:

```
база      = сумма начислений учеников этой группы за месяц   (MonthlyCharge / chargeForMonth)
процент   = процент группы ?? процент преподавателя ?? нет ставки
начислено = округлённое(база × процент)
```

Долг центра перед преподавателем накопительный, как долг ученика перед центром:

```
долг = сумма начислений за все месяцы по месяц M − сумма выплат за те же месяцы
```

База берётся из **начислений**, а не из принятых денег — решение владельца из раздела 0. Практическое следствие, которое надо понимать: преподаватель получает свои проценты и с тех учеников, которые ещё не заплатили. В отчёте по зарплате рядом с суммой показывается «собрано по группе: X из Y» — чтобы администратор видел разрыв, даже если он на зарплату не влияет.

Открытый месяц считается формулой и меняется каждый день (ученик пришёл — база выросла). Закрытый месяц фиксируется и больше не пересчитывается. Это тот же закон, что уже действует для начислений (`isClosedMonth`, `domain/billing.ts:273`), и он же — главная причина следующего раздела.

### 5.2. Где живёт процент

Симметрично цене (`priceFor`): **группа важнее преподавателя**.

```prisma
model User {
  // Ставка преподавателя по умолчанию в базисных пунктах: 4000 = 40 %.
  // Не проценты целым числом: половины процента в договорах встречаются,
  // а менять тип колонки задним числом дороже, чем сразу взять сотые доли.
  salaryPercentBp Int?
}

model Group {
  // Ставка по этой группе; важнее ставки преподавателя. Пусто — берётся его
  // ставка. Меняется только вперёд: закрытые месяцы уже зафиксированы
  // со своим percentUsed.
  salaryPercentBp Int?
}
```

Ставки нет ни там, ни там — зарплата не начисляется, а в отчёте строка помечается «ставка не задана». Молчаливый ноль здесь недопустим: он неотличим от «месяц был пустой».

### 5.3. Новые модели

```prisma
/// Начисление зарплаты преподавателю за календарный месяц по одной группе.
///
/// Зачем отдельная таблица, а не расчёт на лету: Enrollment.groupId и
/// Group.teacherId хранят ТЕКУЩЕЕ состояние. Ученик, переведённый в другую
/// группу в ноябре, утащил бы туда свои октябрьские начисления, и зарплата
/// преподавателя за закрытый октябрь задним числом упала бы. Ровно от этого
/// MonthlyCharge защищает начисления учеников — здесь тот же приём.
model TeacherSalaryAccrual {
  id String @id @default(cuid())

  teacherId String
  teacher   User   @relation("TeacherSalaryAccruals", fields: [teacherId], references: [id], onDelete: Cascade)

  courseId String
  course   Course @relation(fields: [courseId], references: [id], onDelete: Cascade)

  // Пусто — начисление по записям курса без группы
  groupId String?
  group   Group?  @relation(fields: [groupId], references: [id], onDelete: SetNull)

  // Снимок филиала: группу могут перевести, отчёт по филиалу меняться не должен
  branchId String?

  month String // "YYYY-MM" строкой, как MonthlyCharge.month и Payment.forMonth

  base          Int // сумма начислений учеников за месяц
  percentUsed   Int // базисные пункты, по которым посчитали
  amount        Int
  studentsCount Int

  // Сумма, зафиксированная администратором вместо формулы: болезнь, отпуск,
  // разовая договорённость. Заполнена — формула отступает (как
  // Enrollment.firstMonthCharge в начислениях учеников)
  manualAmount Int?

  lockedAt  DateTime?
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt

  @@unique([teacherId, courseId, groupId, month])
  @@index([month])
  @@index([teacherId])
  @@index([branchId])
  @@index([lockedAt])
}

/// Выплата преподавателю. Журнал, а не счёт: правок суммы нет, ошибочную
/// запись помечают deletedAt и вносят заново — как Payment.
model TeacherPayout {
  id        String        @id @default(cuid())
  amount    Int
  method    PaymentMethod @default(CASH)
  paidAt    DateTime
  forMonth  String? // за какой месяц платят, "YYYY-MM"
  comment   String?
  branchId  String?
  deletedAt DateTime?
  createdAt DateTime      @default(now())
  updatedAt DateTime      @updatedAt

  teacherId String
  teacher   User   @relation("TeacherPayouts", fields: [teacherId], references: [id], onDelete: Cascade)

  createdById String
  createdBy   User   @relation("RecordedPayouts", fields: [createdById], references: [id])

  @@index([teacherId])
  @@index([paidAt])
  @@index([forMonth])
  @@index([deletedAt])
}
```

**Ловушка `NULL` в уникальном ключе.** В `@@unique([teacherId, courseId, groupId, month])` поле `groupId` необязательное, а в Postgres `NULL <> NULL` — две строки с пустой группой пройдут обе. Проект уже наступал на это с `AttendanceSession` и закрыл частичным индексом (`prisma/migrations/20260916090000_attendance_no_group_unique`). Здесь нужно то же, руками в миграции:

```sql
CREATE UNIQUE INDEX "TeacherSalaryAccrual_no_group_unique"
  ON "TeacherSalaryAccrual" ("teacherId", "courseId", "month")
  WHERE "groupId" IS NULL;
```

### 5.4. Кому начисляется и историчность

Преподаватель группы определяется той же лестницей, что и в посещаемости (`attendance-access.ts:30`): **педагог группы → педагог курса**. Для записей без группы — педагог курса.

Заморозка закрытого месяца ленивая: строка создаётся при первом обращении к зарплате после конца месяца. Кроме того, заморозку **обязательно** надо вызывать перед каждым изменением входов расчёта — иначе месяц, который никто не открывал, зафиксируется уже по новым данным. Места, куда добавляется вызов (рядом с существующим `ledger.freezeClosedMonths`, строго после него — зарплата опирается на начисления):

| Действие | Файл | Что поедет без заморозки |
|---|---|---|
| Смена педагога, цены, расписания или дат группы | `groups.service.ts:126` | Новый педагог получит зарплату за чужой прошлый месяц |
| Перевод ученика в другую группу | `groups.service.ts:209`, `:258` | Начисления ученика уедут в новую группу вместе с процентом |
| Удаление ученика из группы / отчисление | `groups.service.ts:239` | База прошлых месяцев уменьшится |
| Удаление группы | `groups.service.ts:158` | Строки потеряют `groupId` (`SetNull`), но суммы останутся — ради этого и снимок |
| Смена преподавателя курса | `courses.service.ts` (`update`) | То же для записей без группы |
| Смена `salaryPercentBp` у группы или преподавателя | `groups.service.ts`, `users.service.ts:108` | Новый процент перепишет прошлое |

### 5.6. Порядок расчёта в сервисе

1. Собрать «единицы начисления»: активные группы (с их педагогом и филиалом) и курсы, у которых есть записи без группы.
2. Для каждой — вызвать `BillingLedgerService.resolveSchedules` с фильтром `{ groupId }` / `{ courseId }`. Он сам заморозит закрытые месяцы учеников; база берётся уже из реестра.
3. `percentUsed` = процент группы ?? процент преподавателя; нет — строка с пометкой «ставка не задана», `amount = 0`.
4. `amount` = `manualAmount`, если задан, иначе `Math.round(base * percentUsed / 10_000)`.
5. Закрытый месяц без строки — создать с `lockedAt` (`createMany` + `skipDuplicates`, как в `billing-ledger.service.ts:170`); со строкой — взять из неё.
6. Долг = сумма начислений по месяц M минус выплаты, у которых `forMonth ?? monthKey(paidAt) <= M` — тот же приём, что для оплат учеников (`billing.service.ts:50`).

### 5.8. Что эта модель сознательно не учитывает

Записать прямо в интерфейсе, чтобы потом не выяснять:

1. **Замены.** Если занятие провёл другой преподаватель (`AttendanceSession.teacherId`), деньги за месяц всё равно идут педагогу группы. Отчёт по заменам уже есть (`/attendance/teachers`), администратор компенсирует заменяющему через `manualAmount` или разовую выплату.
2. **Часы.** `AttendanceSession.startedAt`/`endedAt` в расчёте не участвуют.
3. **Пропущенные преподавателем занятия.** Месяц с отметками `ABSENT` начислится полностью; уменьшение — руками через `manualAmount`.
4. **Удержания и налоги.** Не моделируются: журнал выплат фиксирует то, что выдали на руки.

Каждый пункт при необходимости становится отдельной задачей и не ломает схему.

## 7. Открытые вопросы владельцу

Работу они не блокируют — у каждого есть рабочий ответ по умолчанию, но решение лучше принять до начала этапа.

1. ~~Сброс по SMS~~ — **решено 2026-09-20: пока не включаем.** Остаются путь 1 (администратор) и путь 2 (Telegram). Раздел 4.1 про SMS сохранён как заготовка: если понадобится, к нему нужны согласие «код ребёнка уходит основному родителю» и разовая чистка родительских номеров из карточек учеников.
2. **Самостоятельная регистрация.** По умолчанию страница `/register` убирается совсем: учеников заводит администратор. Если самозапись всё-таки нужна публично, её надо делать по телефону с SMS-кодом — по почте она в Узбекистане не работает.
3. **Видит ли преподаватель базу.** По умолчанию на `/salaries/me` показывается и база (сколько начислено его ученикам), и процент. Если преподаватель не должен знать цены и состав платежей — показываем только итоговую сумму.
4. **Шаг процента.** По умолчанию ставка вводится с одним знаком после запятой (40 %, 42,5 %). Если дроби не нужны, поле ограничивается целыми — тип колонки от этого не меняется.
5. **Ограничивать ли список курсов по филиалу.** Курс к филиалу не привязывается (раздел 3.3). Если в формах мешают курсы, которые в этом филиале не ведутся, есть два способа без дублирования уроков: фильтр «курсы, где есть мои группы» или связка многие-ко-многим «курс предлагается в филиалах X, Y».
6. **Зарплата за месяц, в котором преподаватель не вёл занятий.** По умолчанию начисляется по формуле, уменьшается руками через `manualAmount`. Альтернатива — автоматически учитывать долю проведённых занятий из `AttendanceSession`; это отдельная задача поверх этапа 3.
