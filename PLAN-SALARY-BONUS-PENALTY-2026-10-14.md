# План: премии и штрафы преподавателям — 2026-10-14

Администратор должен иметь возможность начислить преподавателю премию или
удержать штраф за месяц. Сейчас зарплата складывается только из процента
от начислений групп, а выдача денег записывается в журнал выплат. Отдельной
суммы «сверху» или «минусом» в системе нет.

## 1. Анализ: как устроено сейчас

**Начислено.** `SalaryService.unitSchedule` считает по каждой «единице»
(группа или курс без группы, плюс заменяющие) суммы по месяцам: закрытые
месяцы берутся из реестра `TeacherSalaryAccrual` (заморожены), текущий — по
формуле. У строки реестра есть `manualAmount`: ручная фиксация суммы целиком.

**Выплачено.** `TeacherPayout` — журнал выдачи денег (сумма, способ, дата,
`forMonth`, комментарий). Правок нет: ошибочную запись удаляют мягко
(`deletedAt`) и вносят заново. Месяц выплаты — `payoutMonth`
(`forMonth`, иначе месяц `paidAt`).

**Долг на месяц M** = всё начисленное по M включительно − все выплаты с
`payoutMonth ≤ M`. Так считают оба места:
- `overview` (`GET /salary`, страница `/salaries`) — строка на преподавателя:
  база, начислено за месяц, выплачено, долг;
- `teacherDetail` (`GET /salary/:teacherId` и `GET /salary/me`) — итоги
  «начислено / выплачено / долг», разбивка по группам, журнал выплат.

Ещё читают зарплату:
- `FinanceService` (отчёт «Финансы»): `salaryAccrued` по месяцам через
  `accrualsByMonth` → прибыль по начислению = начисления учеников −
  зарплата; кассовая прибыль = поступления − выплаты;
- карточка «Моя зарплата» на дашборде преподавателя (`salary-card.tsx`) —
  берёт `paidTotal`/`debt` из того же `teacherDetail`.

**Почему не подходят существующие поля:**
- `manualAmount` — фиксация суммы одной группы за один месяц. Премия
  растворилась бы в ней: не видно ни причины, ни что это премия, а
  «Пересчитать» и снятие фиксации её стирают. И штраф за опоздание к
  конкретной группе не относится.
- Выплата с отрицательной суммой — смешивает «сколько заработал» и «сколько
  выдали», ломает кассу в «Финансах» (выплата = деньги из кассы).

**Данные на проде (2026-10-14):** одна выплата, ни одной ручной фиксации.
Переносить нечего, обходных «премий через комментарий» нет.

## 2. Решение: отдельный журнал корректировок

Новая сущность — «корректировка зарплаты»: премия (+) или штраф (−)
преподавателю за месяц, с обязательной причиной. Это часть **начисленного**,
а не выдачи денег.

Формулы после изменения:
- **Начислено за месяц** = по группам (как сейчас) + премии − штрафы этого
  месяца.
- **Долг на месяц M** = начислено по M включительно (с корректировками) −
  выплаты по M включительно.
- Штраф больше начисленного допустим: долг может уйти в минус (переплата),
  так же как сегодня при выплате больше долга.

Правила журнала — как у выплат: суммы не правятся, ошибочную запись удаляют
мягко и вносят заново; каждое действие — в `AuditLog`.

## 3. Решения, которые нужно подтвердить владельцу

Ниже — что я предлагаю; в скобках альтернатива.

1. **Премия/штраф привязаны к преподавателю и месяцу, не к группе.**
   (Альтернатива — к группе: усложняет, а штраф за опоздание или премия за
   месяц к группе обычно не относится.)
2. **Преподаватель видит свои премии и штрафы с причиной** на «Моя
   зарплата» и в итогах на дашборде. Иначе его «начислено» и «долг» не
   сойдутся с тем, что он получает на руки. (Альтернатива — скрыть, но тогда
   преподавателю придётся показывать числа без корректировок, и они
   разойдутся с суммами у администратора.)
3. **Причина обязательна** (до 500 символов).
4. **В «Финансах» корректировки входят в «Зарплата начислена»** — прибыль
   по начислению учитывает премии и штрафы. Кассу (поступления − выплаты)
   не трогают: деньги двигает только выплата.
5. **Месяц корректировки — любой** (прошлый, текущий, будущий), как
   `forMonth` у выплат. Заморозку закрытого месяца корректировка не трогает:
   это отдельная строка, а не правка `TeacherSalaryAccrual`.
6. **Уведомление в Telegram — не делаем** в этом заходе.

## 4. База данных

```prisma
enum SalaryAdjustmentKind {
  BONUS
  PENALTY
}

model TeacherSalaryAdjustment {
  id        String               @id @default(cuid())
  kind      SalaryAdjustmentKind
  amount    Int                  // всегда > 0; знак задаёт kind
  month     String               // "YYYY-MM"
  reason    String
  deletedAt DateTime?
  createdAt DateTime             @default(now())

  // Restrict, как у TeacherPayout: денежная история
  teacherId String
  teacher   User    @relation("TeacherSalaryAdjustments", fields: [teacherId], references: [id], onDelete: Restrict)

  // Снимок филиала преподавателя на момент записи — как у TeacherPayout
  branchId String?
  branch   Branch? @relation(fields: [branchId], references: [id], onDelete: SetNull)

  createdById String
  createdBy   User   @relation("RecordedSalaryAdjustments", fields: [createdById], references: [id])

  @@index([teacherId, month])
  @@index([deletedAt])
}
```

- Миграция `2026101410xxxx_teacher_salary_adjustments`: только `CREATE TYPE`
  и `CREATE TABLE`, существующие данные не меняются. Один деплой.
- Сумма хранится положительной, знак — из `kind`: в базе и интерфейсе нельзя
  получить «штраф −50 000» с двойным минусом.
- `users.service.ts:601` (проверка перед окончательным удалением
  пользователя) — добавить подсчёт корректировок рядом с выплатами, иначе
  удаление упадёт на внешнем ключе вместо понятной ошибки.

## 5. API (`api/src/modules/salary`)

Новый `AdjustmentsService` рядом с `PayoutsService`, тот же стиль:

| Маршрут | Право | Что делает |
|---|---|---|
| `POST /salary/adjustments` | `manage Salary` | создать: `teacherId`, `kind`, `amount` (> 0, целое, ≤ 1 млрд), `month`, `reason` (1–500) |
| `DELETE /salary/adjustments/:id` | `manage Salary` | мягкое удаление; уже удалённая или несуществующая — 404 |

Маршруты объявить ДО `:teacherId` в контроллере (как `payouts`).

Доменная функция в `domain/salary.ts`:
`adjustmentSigned(a) → +amount | −amount` и
`sumAdjustments(list, { upTo?: month, only?: month })` — тест в `salary.spec.ts`.

Изменения в расчётах:
- **`teacherDetail`**: загрузить живые корректировки преподавателя; в ответ
  добавить `adjustments: [{ id, kind, amount, month, reason, createdAt,
  createdBy }]` (все, по убыванию месяца), `adjustmentsTotal` (сумма со
  знаком по месяцам ≤ M) и учесть её в `accruedTotal` и `debt`.
  Отдельно — `accruedFromGroups` (как раньше), чтобы интерфейс мог показать
  «по группам X + премии Y − штрафы Z».
- **`overview`**: для каждого преподавателя — корректировки месяца M
  (`row.adjustments`, со знаком) и за всё время до M включительно (в
  `accruedTotal` → `debt`). `row.accrued` = группы + корректировки месяца.
  Преподаватель без групп, но с корректировкой, должен появиться в сводке
  строкой (сейчас строки строятся только из единиц). Фильтр по филиалу —
  по снимку `branchId` корректировки, с той же оговоркой, что у выплат.
  Итоги `totals.accrued/debt` — с корректировками, плюс `totals.adjustments`.
- **`accrualsByMonth` / `FinanceService`**: добавить корректировки к
  `salaryAccrued` своего месяца и к `accrued` преподавателя за месяц.
  Кассу не трогать.

## 6. Web

- `src/lib/api/salary.ts`: типы `ApiSalaryAdjustment`, поля в ответах,
  `createSalaryAdjustment`, `deleteSalaryAdjustment`.
- **`/salaries/[teacherId]`** (администратор):
  - рядом с «Выплатить» кнопка «Премия / штраф» → диалог по образцу
    `create-payout-dialog.tsx`: переключатель «Премия | Штраф», сумма,
    месяц (по умолчанию выбранный на странице), причина;
  - под итогом «Начислено» мелкая строка «по группам X · премии +Y · штрафы −Z»
    (если корректировок нет — строку не показывать);
  - новый блок «Премии и штрафы» между группами и журналом выплат: месяц,
    тип (зелёный «+» / красный «−»), сумма, причина, кто внёс, удалить с
    подтверждением.
- **`/salaries`** (сводка): колонка «Премии/штрафы» за месяц (со знаком,
  пусто при нуле) между «Начислено» и «Выплачено»; «Начислено» уже включает
  её — подпись колонки поясняет.
- **`/salaries/me`** и карточка на дашборде преподавателя: блок «Премии и
  штрафы» только для чтения, итоги из того же ответа (`teacherDetail`), без
  кнопок.
- Переводы ru и uz (латиница), namespace страниц зарплат; JSON не
  переформатировать.
- Телефон 360px: таблица корректировок прокручивается внутри блока, диалог
  в одну колонку.

## 7. Тесты

Unit (`salary.spec.ts`): знак премии/штрафа, суммирование по `upTo` и
`only`, удалённые не учитываются.

e2e (`api/test/salary.e2e-spec.ts`, свои данные):
1. ADMIN создаёт/удаляет — 201/200; TEACHER — 403; аноним — 401.
2. Валидация: `amount ≤ 0`, пустая причина, плохой месяц, несуществующий
   преподаватель → 400/404.
3. `teacherDetail`: премия в M увеличивает `accruedTotal` и `debt`; штраф
   уменьшает; корректировка за M+1 не входит в итоги M; удалённая не входит.
4. `GET /salary/me`: преподаватель видит свои корректировки и не видит
   чужие.
5. `overview`: колонка месяца, долг; преподаватель только с премией
   (без групп) есть в сводке.
6. Штраф больше начисленного → долг отрицательный, без ошибок.
7. Финансы: `salaryAccrued` месяца включает корректировки; `paidOut`
   (касса) — нет.
8. Удаление пользователя с корректировками — понятный отказ, а не 500.

`cd api && npm test` и линтер api — зелёные.

## 8. Порядок работы

1. Владелец подтверждает раздел 3.
2. `middle`: схема + миграция + API + доменные функции + тесты.
3. Проверка ведущим: дифф, формулы долга в трёх местах, права, миграция.
4. `middle`: web (страница преподавателя, сводка, «Моя зарплата», дашборд,
   переводы).
5. Проверка ведущим, затем `git-agent`, коммиты:
   - `feat(salary): премии и штрафы преподавателям (схема и api)`
   - `feat(salaries): премии и штрафы на страницах зарплаты`
   Пуш и деплой — по команде владельца.

## 9. Вне плана

- Премия/штраф в процентах, шаблоны причин, повторяющиеся (ежемесячные)
  премии.
- Привязка к группе или к конкретному занятию.
- Уведомление преподавателя в Telegram.
- Правка суммы существующей записи (только удалить и внести заново).
